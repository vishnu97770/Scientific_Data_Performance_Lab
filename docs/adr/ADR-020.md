# ADR-020: Loaders validate the schema and never cast; generator is versioned

**Status:** Accepted (engineering decision, 2026-10-16, from the project specification)

## Context

Loaders originally returned whatever NumPy produced. A wrong-dtype `.npy`, a CSV with a wrong header or a value such as `1.0` in an integer column, or an out-of-range `int16` (which NumPy 2.1 wraps with only a DeprecationWarning) would have been accepted and only caught later, if at all. The dataset generator had no explicit version.

## Alternatives considered

Validate only in `sdplab.validate` against the regenerated dataset (kept as well, for bit-exactness); validate inside the timed region only for some variants.

## Decision

Every loader checks the schema (type, canonical `EVENT_DTYPE`, 1-D; CSV header; exactly one `events` archive member) and raises `FormatError` (a `ValueError`) for wrong, corrupt or truncated input, wrapping low-level parser errors. The CSV parse runs with `DeprecationWarning` treated as an error so behaviour does not depend on the NumPy version. Loaders own their file handle (NumPy leaks it on corrupt input). A missing file raises `FileNotFoundError`. The checks are O(1) metadata comparisons. `dataset.GENERATOR_VERSION` is part of every dataset record and is bumped when generated values change; `sdplab check-run` validates a finished run from its raw files.

## Consequences / trade-offs

Loading rejects non-conforming files instead of repairing them. The tiny metadata check sits inside the timed region of `load`.
